# Changelog

All notable changes to OpenSignup are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- An organizer who opens their own signup's public link now sees a strip across the top of the page (#647), styled like the organizer app's header and above the brand mark, outside the page's content: "**Your signup.** Only organizers see this bar.", with **See responses** and **Edit signup**, which go to the signup's Responses and Build tabs. Screen readers meet it as an "Organizer" navigation landmark. It shows on an open or closed signup to any member of the signup's workspace, viewers included, who is signed in on that browser. Participants see no change, and neither does an organizer from another workspace. The page now reads the organizer's session; a visitor with no session cookie still costs it nothing, since Auth.js answers without the database, and a signed-in organizer's visit sends two more statements (the session and their workspaces), which `budgets.json` pins as its own case.
- `pnpm oauth:keys rotate` and `pnpm oauth:keys retire <kid>` rotate the key that signs connected AI assistants' access tokens (#564). `rotate` adds a key and lists the active ones; after it, restart every web instance and wait 16 minutes. `retire` refuses an unknown key, and refuses an old key until a newer one has been signing for an access token's lifetime plus the verifier's 15 seconds of clock tolerance, which catches a forgotten restart; it can only see that one instance moved to the new key, so with several instances every one still has to be restarted first. `retire --force <kid>` retires a leaked key at once, at the cost of one refresh for each connected assistant, and still refuses the newest key. Each instance now records when it starts signing with a key (a new `signing_since` column on `oauth_signing_keys`, added by migration `0013`), and re-reads its signing keys from the table every 5 minutes, in the background, as well as on an unknown key, so a retired key stops being trusted without a restart; if that re-read fails, it keeps verifying with the keys it holds. Requests that need the keys at the same time share one read. Neither the CLI nor the server log prints a failed key query's parameters, which for a new key include its private half. The steps are in `docs/connect-ai-assistant.md`. In the Docker setup, run it as `docker compose exec web pnpm oauth:keys …`.
- Magic Compose asks a few questions when a description doesn't say what people sign up for (#570). A description that is only an event's name, like "Bake sale", used to get three "TBD" rows or made-up jobs. Now the AI answers with the topics the description leaves out (what, when, how many) and two to four suggestions for what people could sign up for, in the description's language; it never suggests dates or counts, which the page asks for with its own controls. The organizer's answers go back with the description, and that second call always drafts or refuses, with "TBD:" rows for anything left blank and for **Draft with placeholders**. A description that says what but not when or how many still drafts straight away, with "TBD:" rows where the slots need dates or times, and a list of items, roles or tasks, or a schedule of dated practices or shifts, counts as saying what. A first reply with questions the page can't show (no "what", or one usable option) is tried once more on the same quota, and extra options are cut to four. A slot gets no limit only when the description or the answers say there's none. Both calls count toward the hour's AI drafts, so the limit goes from 10 to 12 an hour. The privacy page now says the answers go to the AI provider along with the description. `pnpm eval:magic-compose` scores questions: a case can expect them (`questions.*` checks), or give `answers` to send after a first call that must ask, and the draft made from them is scored. `ev_008`, the vague team prompt, now expects questions instead of 1-6 placeholder slots (and is about a swim club, not the soccer team of the prompt's own example, so it scores the rule rather than recall), and ten new made-up cases cover prompts that must ask, near misses that must still draft, and drafts from answers. `pnpm eval:mcp` passes an assistant that asks the organizer on those cases and skips the ones with answers.
- Activity events for Magic Compose's questions (#570), so drafts that stop there can be counted. `magic_compose.asked` (`{ topics, options }`) is written when a first draft comes back with questions instead, and one `magic_compose.answered` for each call that carried the organizer's answers, however it ended, with `{ answered, skipped, picked, added, limits, placeholders, retried, gaveUp }`: which of "what" and "when" were answered or left blank, how many of the AI's options were picked and how many things of their own were added (as the browser reports them), how many were given a number of people, whether Draft with placeholders was pressed with nothing answered, and whether the AI asked again and was retried or given up on. Both are written outside any transaction, with no signup. Payloads hold codes and counts only, never the description, the options or the answers. `docs/telemetry.md` lists them, and the privacy page says the log records them.
- After **Publish and share**, a panel helps the organizer send the link, in place of the "Signup published" banner (#505). It says "Published" and "Now send people the link", and offers **Copy link**; a message to send with it, built from the signup's own data, such as "Fall book fair volunteers / Thu, Nov 12 to Sat, Nov 14 · 21 spots open / Sign up here, no account needed: <link>", which the organizer can change and which stays changed while the page is open; **Copy message** and **Email it**, a `mailto:` link with the title as its subject and the message as its body, less its first line when that is the title; and a QR code to **Download** as a PNG for a flyer or a sign-up table, with the signup's title under the code in up to two lines, shown only where the browser can draw it. The message's dates come from the date field reminders use. Days in a row read as a range, "Thu, Nov 12 to Sat, Nov 14"; two or three days with a gap are named, "Sat, Nov 7 and Sat, Nov 14" or "Sat, Nov 7, Sat, Nov 14 and Sat, Nov 21"; four or more read as a range again. When every dated slot has the same value in the time field reminders pair with that date, the message gives it: "Sat, Nov 21, 11:00 AM · 19 spots open" for one day, "Thu, Nov 12 to Sat, Nov 14 · 11:00 AM · 21 spots open" for several. The days and the time come from the slots people can still take, as the spots do (open, with a spot left or no limit), so a closed or full slot adds no day and hides no time; when none has room they come from the open slots, and when none is open from every slot. It counts spots, not slots, since readers don't know the organizer's word "slot": "21 spots open" before anyone signs up, "18 spots left" after, and no count when an open slot has no limit or no spot is left. A signup with no dates and no limits gets only its title and the link. The description stays out, since a link preview shows it. On a phone that has a share menu, **Share…** comes first and opens it with the message and link, in place of Copy message and Email it. On a phone, **QR code** shows the code large in the sheet, under the Copy link row, and then looks pressed and says **Hide QR code**, since the code pushes the message below the screen; **Save image** is under the code: where the phone can share a file it opens the share menu with the PNG, so it can go to Photos, and the menu says where it went; elsewhere, or if the phone refuses, it downloads and says "Saved". The message box is labelled "A message to send with it" on a phone and a computer, and on a computer grows with the message up to 12 rows. Copy message keeps its width while it says "Copied", so Email it doesn't move. On a computer the panel opens under the header's buttons; on a phone it is a sheet. An open signup's header now has a **Share** button that opens the panel again, headed "Share the link": on a computer in the blue spot right of **Preview**, before ⋯, and on a phone in the bar at the bottom of the screen. Publish now stays on the tab it was pressed on instead of going to Build with `?published=1`, so a reload or a shared address never opens the panel again. Escape or the panel's ✕ closes it and puts focus back on Share, as does a tap outside the sheet on a phone; on a computer a click outside closes it and leaves focus where it landed. Each copy is announced, and a copy the clipboard refuses (a site served over plain HTTP, a denied permission) says "Couldn’t copy. Select the link and copy it." and selects the link. When Publish on this page has published the signup, screen readers hear "Published. Anyone with the link can sign up now."; a signup published elsewhere, such as by an AI assistant, doesn't open the panel or say so. The QR code is drawn in the browser by `lean-qr` 2.7.4 (MIT, no dependencies); it and the rest of the panel load once a draft's or an open signup's page is idle (in Safari, which can't say when, 200 ms after it's shown), so no page's first load carries them and the panel usually opens at its full size, not on a spinner that then grows; a load that fails is tried again when the panel opens, and if that fails too the panel still shows the public link with its copy button, and "Couldn’t load the other ways to share. Reload to try again." Email it opens the organizer's own email app, and Share… the phone's own menu; the QR code goes to no outside service. Copies and shares from the panel are recorded through the link-copy beacon from #525: Copy link and Copy message as `signup.link_copied` with the surfaces `share_panel` and `share_message` (the fallback's chip counts as `share_panel`), and, as a new `signup.link_shared` event (`share_menu`, `email`, `qr_code`), Share… once the menu says it sent, Email it on its click, and the QR code once each time the panel opens, the first time a phone shows it large or it's first downloaded or saved; a refused copy or a share menu closed without sending records nothing. Each row holds only the surface and the signup's status: never the message, and nothing about who the link went to. `POST /api/signups/[id]/link-events` takes `event=shared` and refuses a surface that isn't its event's, `docs/telemetry.md` lists the new event and surfaces, and the privacy page says the log records these. The help page "Create and publish your first signup" says what the panel offers.
- The AI connector can reopen a closed signup, with a new `reopen_signup` tool (#20). It calls the same `reopenSignup` as `POST /api/signups/[id]/reopen`, and its result shows `closesAt` as null when a closing time that had passed was removed. `close_signup` no longer says closing can't be undone, and the help page "Connect an AI assistant" lists reopening among what an assistant can do. The assistant isn't told to ask before reopening, as it is before closing: a reopen only follows the organizer asking for one, and closing undoes it.
- A closed signup can be reopened (#20), through `POST /api/signups/[id]/reopen`. It takes sign-ups again at the same link, and everyone already signed up keeps their spot. Only a closed signup reopens: a draft is published as before, and an archived one stays archived. A closing time that has already passed is removed, since it would go on turning everyone away; one still to come is kept. `GET /api/signups/[id]` lists it in `_links` as `reopen`. A signup that isn't closed is refused with `conflict` on `status` ("cannot reopen a signup that is open"), and one with no slots left with `conflict` on `slots` ("reopen requires at least one slot"). Each reopen writes a `signup.reopened` activity row (`{ from, to }`, plus `clearedClosesAt` with the removed time).
- The web app can reopen a closed signup (#20), with **Reopen signup**: on a computer, the blue button beside **Preview** in the signup's header, where a draft has **Publish and share**; on a phone, an item in the ⋯ menu under **Preview**, which a closed signup now keeps. On a phone it's behind ⋯ rather than in the bar at the bottom of the screen, since Close signup's question opens there and a second tap would reopen what it had just closed. It reopens the signup at the same link, everyone already signed up keeps their spot, and a closing time that has already passed is removed, as for `POST /api/signups/[id]/reopen`. It doesn't ask first. Once it has reopened the signup, the header shows the signup open with its Share and ⋯ again, focus moves to the signup's title, and screen readers hear "Reopened. People can sign up again."; no share panel opens, since the link was shared when the signup was first published. A signup reopened some other way, such as by an AI assistant, says nothing. A refusal shows on its own line under the header on a computer, as Publish's does, so Preview stays beside the button, and under the item on a phone: "You don’t have edit access." for a viewer, "This signup changed since the page loaded. Reload to see the latest." when it's no longer closed, "Add a slot before reopening." when it has no slots left, "This signup is no longer available." when it was deleted meanwhile, and otherwise "Couldn’t reopen the signup. Try again." Focus goes back to the button after a refusal, and a second press hides the last refusal while it's in flight.
- A new help page, "Close or reopen a signup" (#20), walks through closing a signup from the ⋯ beside **Share** (beside the title on a phone) and reopening it with **Reopen signup**, beside **Preview** (behind the ⋯ on a phone). It says what changes while it's closed: nobody new can sign up, people see "Closed" at the top and on each slot that isn't full, everyone already signed up keeps their spot and can still change their details or cancel, reminder emails go out as before, and the link stays the same. Reopening asks nothing first, sends no email, and removes a closing time that has passed. Its walkthrough follows the steps on a computer and on a phone, and the help index's description now lists closing and reopening.
- Activity events for the steps where new organizers stop (#500), so they can be counted: `signup.link_copied` when an organizer copies a signup's link from its header (sent from the browser to `POST /api/signups/[id]/link-events`, which takes only a signed-in member of the signup's workspace, 60 an hour each), `magic_compose.failed` with the AI draft's error code, `refusal`, `not_saved` or `over_limit`, and `signup.publish_refused` when a publish is turned down for having no slots or because the signup was closed or archived meanwhile, from the browser, the API or a connected assistant. A publish of a signup that's already open isn't counted as refused. The publish refusal for a signup with no slots now names `field: 'slots'`. The organizer's page views (`signup.draft_started`, `signup.viewed` on the Build tab, `signup.editor_opened`, `signup.previewed`) now say whether they were opened on a phone or a computer (`device`), and `signup.draft_started` says which form the page showed (`mode: 'magic' | 'manual'`). Payloads hold codes and kinds only: no prompt, no email, no User-Agent. `docs/telemetry.md` lists them, and the privacy page says the log records these.
- Participants are emailed when the organizer moves their slot to a new date or time (#524). The email ("Time changed: <signup> · <slot>") prints the slot's new details and the participant's link to change or cancel, and goes about 10 minutes after the organizer's last change, so a date and then a time, or a date typed day by day, send one email for where the slot ended up, and a slot moved back before then sends none. It follows the reminders setting: with reminders off, or for someone who unsubscribed, nothing is sent, and the unsubscribe link and page now say they stop these emails too. A reminder for a time the participant was already told about reads as a normal "Reminder"; "Time changed" now means their last email, whatever it was, was for another time. Moves are made through the Build tab, a group heading or the `update_slot` tool; a field change that re-times every slot (a deleted time field, a new reminder date) sends nothing. In the Build tab, a slot's editor now says how many people are signed up for it and whether they'll be told if it moves. Each move writes a `slot.rescheduled` activity row (`{ slotId, from, to }`) and each email a `slot.change_sent` row. The worker gains two queues, `slot-changes.dispatch` (every 2 minutes) and `slot-changes.send`; it creates them itself when it starts, so there is nothing to migrate.
- `pnpm eval:mcp`, an opt-in eval of what a connected AI assistant builds through the MCP tools (#254). It sends each case in `evals/magic-compose/dev-evals.json` to a tool-calling model with the server instructions and the tool list, takes the arguments of its `create_signup` call, and scores them with the checks the Magic Compose evals use, now shared in `scripts/lib/eval-harness.ts`. It reuses the `LLM_*` settings and needs no database. Like `pnpm eval:magic-compose`, it is run by hand, never in CI. Two new cases check that a signup for parents at each game gets one dated slot per game, with the right capacity, and no fields for names, emails or what someone brings.
- Follow-up cases for `pnpm eval:mcp` (#477), in `evals/mcp/followup-evals.json`: the organizer says more after the assistant has made the signup, as in "add an earlier slot for setup", "each dish needs to feed 20 people, about 200 people in total" and "show me what you made". A case lists those messages in `followUps`. Every tool call in these cases is answered by the real MCP tools against the local Postgres (`DATABASE_URL`, as for `pnpm test:db`), with a new organizer and workspace for each case, and the case is scored on the tools called after the first message, the signup's slots before and after, and the last reply (a Markdown table with a row per slot, and `links.edit`). The single-message cases run as before and still need no database. `pnpm eval:mcp --tag=follow_up` runs only the new ones.
- An instance can add its own links to the site footer, shown before Help, by listing them in `src/lib/footer-links.ts`. The list is empty here, so the footer is unchanged; a deployment that serves pages of its own fills in its own copy, and every page links to them without that deployment editing the footer.
- Organizers can take one person off a slot (#377). Each active row on the Responses tab has a **Remove** button, named for screen readers by the person and slot ("Remove Sam Example from Fruit and water"), which asks first ("Remove Sam Example from Fruit and water? Their spot opens up for someone else. They won't get an email about it.") and then cancels that one sign-up, so its spots open up again. The question opens in a dialog over the table, so the table doesn't move and nothing behind it can be used until it closes; Escape or **Keep** closes it and returns to Remove. On a screen narrower than 768px, where the table didn't fit, each person is a card instead: name and status, then the slot, then the email and Remove, with nothing to scroll sideways. Status is a coloured label everywhere, green for confirmed and grey for cancelled, removed or moved, so a row without Remove says why. On a phone, Remove, **Keep** and **Yes, remove** are 44px tall, and the dialog fits the screen. Until now the only way was to delete the whole slot, taking everyone on it. The person gets no email; their edit link says "The organizer took you off this slot" and names the slot, also when they had moved there from another slot, and the public page no longer shows them as signed up. Their row stays on the Responses tab with the Status "removed"; the old row of a move to another slot now says "moved" rather than "cancelled", and the tab's count leaves out every cancelled sign-up (the CSV export keeps the stored status). Owners, admins and editors can remove someone; a viewer is told "You don’t have edit access.", and someone whose slot or signup was deleted meanwhile gets "This person is no longer on this signup. Reload to see the latest." Removing someone already cancelled changes nothing. A new help page, "Take someone off a slot", walks through it. Each removal writes a `commitment.removed` activity row (`{ commitmentId, participantId, slotId }`) by the organizer, in the same transaction as the cancel; `event_type` is plain text, so no migration is needed.
- Landing-page CTA click telemetry (`landing.cta_clicked` activity event).
- Initial v1 scaffolding: Next.js 15 + TypeScript + Drizzle + Auth.js v5 + pg-boss.
- Full entity schema (workspaces, organizers, members, signups, slot groups, slots, participants, commitments, activity, magic links, claims).
- Zod schemas as source of truth with discriminated union on `slot_type`.
- Capacity-safe commitment service with `(slot_id, position)` unique enforcement.
- Organizer magic-link login and personal-workspace auto-create.
- Mobile-first participant page with bottom-drawer commit flow.
- Reminder emails the day before a dated slot, via pg-boss.
- Pluggable email transport: console, SMTP, Resend.

- Organizers can let participants sign up without an email (#378). The signup's `requireEmail` setting, on by default, is set on the Settings tab, in a new "Sign-up form" section: "Ask for an email address", Required or Optional, then Save. The AI connector's `update_signup` tool and `PATCH /api/signups/[id]` can set it too. A line under the choices says what the one picked means, and changes as soon as the radio does: with Required, everyone is emailed their link to change or cancel; with Optional, people who leave it blank get no emails, not even reminders, so they need to save their link, and someone who loses it can sign up again while the organizer removes the old one on the Responses tab. A viewer is refused with "You don’t have edit access.", the words the Build tab now uses too in place of "You no longer have edit access.", and a refused Delete on the same tab is put in the same plain words instead of the service's own message. With it off, the sign-up form's Email box says "(optional)" and starts blank, even for someone this browser remembers. Its help says what an email brings (the link, and a reminder only where that slot will get one) and to save the link without one. Someone who leaves it blank gets no confirmation or reminder emails. Their link to change or cancel is not emailed: the confirmation screen shows it, says to save it and offers Copy link in place of Share link, which on a phone invited them to post it, and the `os_commit` cookie keeps it in that browser. If the organizer turns it back on after the page loaded, the refused blank email turns the box required. In `POST /api/slots/[id]/commitments`, a blank, whitespace-only, null or missing `email` now means none: a signup that requires one refuses it with `invalid_input` on `email`, and one that doesn't always adds a new participant, as there is nothing to find them by. Turning the setting back on asks only new sign-ups: anyone already signed up without an email keeps their spot and can still change or move it. `get_signup` and the other connector tools now show `requireEmail`; `update_signup` advertises no default for any setting, so a client that fills in defaults cannot turn it back on with an unrelated change. The privacy and cookies pages and the help pages say what happens without an email, and the help page "Create and publish your first signup" explains the setting and what to do when someone loses their link. The "Sorry, this link isn’t working" page tells everyone to contact the organizer, and to try their confirmation email's link only if they got one.

### Changed
- **Publish and share** no longer stops for a slot that says TBD, TBC or TBA (#670). Organizers often mean it ("Cashier TBD", "Location TBA"), so the "Before people see it" question, with **Name it first** and **Publish anyway**, is gone, and the signup publishes straight away. Publish still stops when there's nothing to sign up for: no slots, no fields, or every slot empty. The Build tab no longer marks a slot that says TBD either: the "Still says “TBD”" and "People can see “TBD”" tags, the row's warm tint and the tag's words in the row's accessible name are gone, for drafts and published signups alike, and the help page no longer mentions them. New `signup.published` and `signup.publish_refused` activity rows no longer carry `acknowledged: 'placeholder'` or `{ reason: 'placeholder', warning: true }`; older rows still can (`docs/telemetry.md`).
- Times are picked from a list instead of typed into the browser's time box (#686). On a computer that box is filled in segment by segment (hour, minutes, AM/PM) and doesn't take "9am". The Build tab's Time cell and the "One day" times on Magic Compose's questions screen now use one `TimeSelect`: a list of times every 15 minutes, read on the 12-hour clock as on the public page, with "No time" first. Typing "9" jumps to 9:00 AM, and phones keep their own picker. A time that isn't on the 15-minute grid (09:10, say, from an AI assistant) is listed as itself, so opening a slot never changes it. On the questions screen the two times are now labelled **Starts** and **Ends**; Ends lists only times after the start, each with its length ("1:00 PM (4 hr)"), and clears when the start is moved to or past it. Times are still stored as 24-hour HH:MM, so nothing changes on the server, in emails or in reminders.
- The help page "Close or reopen a signup" now mentions pausing sign-ups in its summary on `/help`, its description and its first paragraph (#653). Organizers looking for a way to pause a signup searched for "pause" and found nothing, because the page only said "close". The page's title, link and the **Close signup** button are unchanged.
- Magic Compose's questions now arrive in the drafting screen instead of replacing it (#570). The screen keeps its steps and panel: "A few details" becomes a step between reading the description and drafting it, the questions take the panel's place where the draft would have appeared, and the heading changes to "A few details first". On a phone the steps shrink to one line so the first question starts on the first screen, and Back sits at the top left. Steps still to come are drawn in readable grey; they were too faint. The new-signup page's JavaScript budget goes from 115 to 116 kB.
- When an organizer has used the hour's AI drafts, the Magic Compose page now says "You've used this hour's AI drafts. Try again in N minutes, or fill it in by hand.", with "fill it in by hand" linking to the manual form, in place of "too many requests — wait Ns and retry" (#570). A 429 from the AI provider itself reads "The AI service is busy. Try again in a minute.", or names the wait when the provider asks for longer. The API's error is unchanged: the page words it from `details.bucket` and `details.retryAfterSeconds`.
- The privacy page no longer says the site sends nothing to an AI vendor by itself (#570). When the operator turns on AI drafting, the description an organizer types is sent to the AI provider the operator configured, and the page's Third parties section now says so, along with what doesn't go with it and how to avoid it (fill the signup in by hand).
- The Magic Compose page says what a draft needs (#570). Its helper line now reads "Say what people sign up for, when, and how many of each." in place of "The more detail you share, the better the draft.", and while the AI works the screen is headed "Reading your description", with "You'll get a draft, or a few quick questions if it needs more to go on.", until a draft arrives and it turns to "Drafting your signup". The description is quoted back in a "You wrote" box instead of a grey quote. The page is also ready for when the AI starts asking questions, which a later change turns on: "A few details first" asks only what the description leaves open, what people sign up for (the AI's options to pick, plus the organizer's own, up to 12), when (one day with optional times, several days, or not decided) and how many people for each (empty for no limit), and offers **Draft my signup**, **Draft with placeholders**, **Fill in by hand instead** and **Back**, which writes the answers into the description as plain lines ("What: Staff the table (2)", "When: Saturday, November 14, 9am to 1pm", or "When: 9am to 1pm" for times with no date yet) so the next draft starts from one text, and puts focus at the end of it. Draft with placeholders makes every topic a placeholder when nothing is answered; once anything is, it sends the answers as Draft my signup does. Both stop on the page, with the reason above the questions and focus moved to it, for an end time before the start time, a date with a short year ("Check the date's year."), times with no date ("Add a date, or leave the times empty.") and a count that isn't a whole number ("Use whole numbers for how many people."), which is no longer rounded. While it drafts from the answers, a "Drafting from" card lists them, a blank one with a grey dashed icon; Cancel and any error come back to the questions with every pick, date and number kept, and a timeout there says "AI drafting timed out. Try again." rather than to try a simpler prompt. The questions screen and that card load only when a reply asks, so the page's first-load JavaScript grows by under 1 kB, for the "You wrote" box and the new steps (its budget goes from 114 to 115 kB). The help page "Create and publish your first signup" gives the new helper line and says what to do when it asks.
- The site footer shows the commit the site was built from, such as `1d4ff3a · OpenSignup · AGPL-3.0`, in place of `v0.1.0`, a version number that never changed (#660). A connected AI assistant gets the same short hash as the MCP server's `serverInfo.version`, and `GET /api/public/health` returns it as `commit`. A build that doesn't know its commit shows no version in the footer, reports `unknown` to assistants and `null` from the health check. A local `pnpm build` takes it from git. The Docker image has no `.git`, so self-hosters pass it as a build arg: `GIT_COMMIT_SHA=$(git rev-parse HEAD) docker compose -f docker-compose.prod.yml up -d --build`, or `fly deploy --build-arg GIT_COMMIT_SHA=$(git rev-parse HEAD)` on Fly. It's optional, and leaving it out doesn't fail the build. `package.json` no longer has a `version`.
- `POST` and `GET /api/signups` now refuse a `workspaceId` that is blank or isn't a string with 400 `invalid_input`, "workspaceId must not be empty" or "workspaceId must be a string", as the AI connector's tools already did (#677). A `workspaceId` of spaces or a number used to reach the policy guard and come back 403 `forbidden`, and an array got past it to the service. With no `workspaceId` and no default workspace, the error now reads "no workspace given and the account has no default workspace" instead of "workspaceId required". A missing or `null` `workspaceId` still means the default workspace, and a valid one works as before.
- **Publish and share** checks the signup before it publishes, and stops only for what the code can prove (#503). - A cancelled sign-up's edit link no longer opens the edit form (#375). The link in the confirmation email never changes, and following it after a cancel showed the form as if the sign-up were still active: Save failed with the API's "commitment is not active", and Cancel signup went through again and changed nothing. With the right token, the page now says "Your spot was cancelled", names the slot ("Run the till · Sat, Nov 14", as the confirmation email's subject does) and links back to the signup, suggesting signing up again only while its slot still takes sign-ups ("There’s still room if you want to sign up again."), and otherwise saying why not: "The signup has closed.", "The slot has closed." or "The slot has filled up since."; a wrong or missing token still gets "Sorry, this link isn’t working". The old link of a sign-up moved to another slot says "Your spot moved to another slot" instead, and links to the sign-up it moved to ("See your new spot"); the privacy page, which said that link stopped working, now says so too. A save refused because the sign-up was cancelled in another tab while the form was open reloads the page, which then says so; the API's "commitment is not active" conflict now carries the commitment's status as `details.status`. An edit link with another signup's slug in it redirects to its own, as the unsubscribe page does, so its back link no longer leads to an unrelated signup. `GET /api/commitments/[id]` still answers for a cancelled sign-up, and now includes `signupSlug`. The page's words follow the help pages: one person's place is a "spot", so "sign-up" no longer sits beside "the signup" in one card, and every whole-page message (cancelled, moved, not found, not published) balances its lines so a heading doesn't leave one word on a line of its own.
- A date field refuses a year before 1900 (#324). It took any four-digit year, and early ones broke things later: Postgres has no year 0, so a slot dated `0000-01-01` failed to save when that field set the slot's time, or broke a later field or settings change that moved the reminder date onto it; a year below 100 was stored correctly but read back a century late (`0099` as `1999`), including by the sign-up lockout check; and "Add to calendar" wrote a year below 1000 with too few digits. The error now says `"<ref>" must be a date in 1900 or later`; a day that doesn't exist, such as `2026-02-30`, still gets `"<ref>" must be a real date as YYYY-MM-DD`. The Build tab's date picker starts at 1900-01-01, the MCP tools' field guide names the floor, and Magic Compose leaves a drafted date that is early or doesn't exist blank, with a warning, where `createSignup` used to refuse the whole draft over it. A slot already holding such a date keeps it: saving that slot's values again asks for a date in 1900 or later, and a rebuild that reaches it gives it no reminder time instead of failing. Migration `0010` sets `slot_at` to null wherever it falls before 1900, so the lockout check and "Add to calendar" stop reading an early or misread instant straight away; the date itself stays in the slot's values. Every database connection the app opens now starts on UTC, whatever the database's default time zone: under a zone whose offset then had seconds in it, such as Amsterdam's before 1937, a slot dated in those years read back as an invalid date, which broke the public page and the lockout check. To see which slots still hold one (read-only): `SELECT s.slug, sl.id AS slot_id, f.ref, sl.values->>f.ref AS value FROM slots sl JOIN signups s ON s.id = sl.signup_id AND s.deleted_at IS NULL JOIN slot_fields f ON f.signup_id = sl.signup_id AND f.field_type = 'date' WHERE sl.values->>f.ref <> '' AND sl.values->>f.ref < '1900';`
- The SMTP login is no longer sent unencrypted when the mail server doesn't offer encryption (#330). On any port but 465, the default 587 included, the app switched to an encrypted connection only if the server offered STARTTLS in its first reply, so a server without STARTTLS, or anyone on the network who removed the offer, got `SMTP_USER` and `SMTP_PASSWORD` in plain text, then the email with its sign-in link and code. With a login set, the app now insists on STARTTLS and fails the send rather than going on without it. The error is "Error upgrading connection with STARTTLS" when the server refuses STARTTLS, or "EHLO failed but HELO does not support required STARTTLS" when it refuses EHLO, and either way it ends "The mail server did not accept STARTTLS. If it takes a login without encryption on a network you trust, set SMTP_REQUIRE_TLS=false." A server without a login is left as it was, deliberately, so a local test mail server with no TLS keeps working; set `SMTP_REQUIRE_TLS=true` to insist on encryption there too. **Before upgrading:** if your mail server takes a login but has no STARTTLS (a relay on your own private network, for example), set `SMTP_REQUIRE_TLS=false`, or every email will fail, sign-in links included.
- Changing "Group slots by" or "Send a reminder email before this date" on the Build tab no longer undoes setting changes made since the page opened (#314). The Build tab sent back its whole copy of the signup's settings from when the page loaded, with one value changed, and `PATCH /api/signups/[id]` replaced the stored settings with it. So a change made in another tab, or by an AI assistant through `update_signup` (turning reminders off, say), was quietly reverted the next time the Build tab saved either control. The Build tab now sends only the setting it changed, and `PATCH /api/signups/[id]` merges the settings it is given over the stored ones, as the AI assistant tools already did: a setting left out keeps its value, and `null` clears it (back to its default, where it has one), except `reminderFromFieldRef`, which keeps its date field whether it is left out or sent as `null`. A script that cleared a setting by leaving it out now has to send it as `null`. After a save the Build tab shows the settings the server returned, so reminders switched off elsewhere no longer still look on there. Two quick changes to these controls are saved one after the other, in the order they were made, so the server applies them in that order and the tab ends up showing the later one's result.
- A sign-in email that times out now has its real outcome logged (#332). The sign-in request stops waiting on a send after 30 seconds, but the send itself keeps going, and how it ended was thrown away, so the log said only "magic link send timed out after 30 s" even when the mail server went on to reject the login or the TLS connection. A send that ends after the limit now logs "magic link send failed after it timed out" with the mail server's error message and code, plus those of the error's cause (where a failed request to Resend keeps the real reason), or "magic link dispatched after its send timed out" when the email did go out, both with the recipient and how long the send took. Only the error's message and codes are logged, never the whole error or the email's contents, and any URL query string or six-digit number in that text is blanked in case the mail server quoted the email. The send is still not cancelled when the limit runs out; that is left for later.
- The sign-in page keeps the email address you typed when it shows an error (#50). It used to clear the box after any error — an address it couldn't read, a link that failed to send, or the sign-in rate limit — so fixing a one-letter typo meant typing the whole address again. Editing the address clears the error. After the rate limit, the button does nothing until the address is edited: every request counts against the IP address's allowance first, which everyone on a shared network shares, and clicking it again and again would use that up. After a link is sent the box still empties, ready for "Send again". The six-digit code box likewise keeps a wrong code, so one mistyped digit no longer means typing all six again.
- SMTP startup now rejects an incomplete credential pair instead of silently skipping authentication (#331). **Before upgrading:** if you set only `SMTP_USER`, add `SMTP_PASSWORD` or remove `SMTP_USER` for a server that needs no authentication; likewise, remove a lone `SMTP_PASSWORD` or add its user. An empty or whitespace-only `SMTP_USER` or `SMTP_PASSWORD` counts as unset. Spaces around `SMTP_USER` are trimmed; the password is used exactly as given, spaces included.
- A setting that holds only whitespace (spaces, a tab, a stray newline, or an invisible character pasted from a secrets dashboard) now counts as unset, the same as an empty one. So startup catches a blank `SMTP_HOST`, `RESEND_API_KEY`, `GOOGLE_CLIENT_ID` or `LLM_MODEL`, where before every email, Google sign-in or Magic Compose request failed later, and a required setting such as `AUTH_SECRET` reports that it is required. The error adds "Its value is only whitespace, which counts as unset." so a value you can't see is not a mystery. Settings with a development default (`EMAIL_TRANSPORT`, `NODE_ENV`, `NEXT_PUBLIC_APP_URL`, `AUTH_MAGIC_LINK_MAX_AGE_MINUTES`) still refuse a blank value rather than falling back to the default.
- The sign-in page no longer says a magic link was sent when sending it failed (#329). When the email can't go out (the mail server is down or too slow, or the request is over the sign-in rate limit), Auth.js logs the error and answers with its error page instead of throwing, and the page counted any answer that wasn't a throw as sent, so it showed "Sent — check your email" for a link that never left. It now counts a link as sent only when Auth.js answers with its check-your-email page, and otherwise shows "Couldn't send. Please try again." A request over the sign-in rate limit (5 links an hour for one address, 20 from one IP address) says so instead, since trying again at once would fail again: "Too many sign-in requests. Wait up to an hour. If we already emailed you a link, you can use that." It has no "Try again" link: every request counts against the IP address's allowance first, which everyone on a shared network shares. The limit counts in fixed hourly windows and applies to every address alike, known or not, so the message says nothing about whether an account exists. `sendVerificationRequest` throws the limit as `MagicLinkRateLimited` (`src/auth/magic-link-rate-limit.ts`), an `AuthError`, which Auth.js rethrows to the page's `signIn`; `POST /api/auth/signin/nodemailer` still answers with `/login?error=Configuration`, as before. The form's error text also shows in red now; it showed grey.
- A participant can no longer take more spots through their edit link once sign-ups have closed. Signing up, and moving to another slot, is refused when the signup is closed or archived, its closing time (`closesAt`) has passed, the slot is closed, or the slot is inside the signup's lockout window (`lockoutHoursBeforeSlot`), but raising the number of spots on a place already held checked none of these. So anyone already signed up could add spots after the organizer closed the signup or the slot. `PATCH /api/commitments/[id]` now refuses an increase with `closed` by the same rules, which signing up and the edit page now share, and logs it as a failed attempt like a refused sign-up. The edit page shows a "Sign-ups have closed" notice and no longer offers more spots than the participant holds, and a save refused because sign-ups closed after the page loaded says "Sign-ups have closed, so you can't add more spots." rather than the API's message. Lowering the number, changing a name or notes, and cancelling still work, since they only give places back or correct details.
- Deleting a signup now also stops its slots, fields, activity log and CSV export being served. The four organizer routes reading those never checked `deleted_at`, so a deleted signup kept answering on its id to members of its workspace — the export with every participant's name and email address — long after it had vanished from the organizer's list and the public page. The slots, activity and export routes now go through one `getSignupRowForOrganizer` in the signups service, and `listFields` behind the fields route checks `deleted_at` too. The activity route's `?limit=` is also rounded down to a whole number; a fraction such as `1.5` used to fail with a 500.
- A deleted signup no longer takes sign-ups or edits. Deleting keeps the signup's status as it was, and signing up checked only that status, so an open signup kept accepting people after it was deleted: anyone with the page still open, or a slot id, could sign up, and got a confirmation email for a signup the organizer thought was gone. Adding, editing or deleting a field, reordering slots and deleting a slot went through as well, each writing to the activity log of a signup that every read calls not found, and a participant's edit link still let them change their place or take more. The organizer's services and signing up now load a signup through `readLiveSignup` or the signup lock (`lockSignupForWrite`) in `src/services/locks.ts`, which both skip a deleted signup, the lock including one deleted while it waited. A participant's edit link is not found, like the signup's own page, including an edit or cancel that was waiting on a lock when the delete landed, and the confirmation email is not sent if the signup has been deleted by the time it goes out. Publishing, closing or archiving a signup that is deleted at the same moment is not found rather than a status change on the deleted row. On the sign-up sheet and the edit page, a slot or signup removed after the page loaded now reads "Sorry, this is no longer available" rather than the API's "not found". The privacy page said deleting a signup removes its commitments; it takes them off the site, but the rows stay in the database until someone asks for them to be erased, and it now says so.
- A post-login `callbackUrl` on `/login` or `/login/check` can no longer send the browser to another site. `safeCallbackUrl` checked the value as a string, but a browser drops tab, LF and CR characters before reading a URL, so a value that passed the check could still arrive as a link to another host. It now parses the value, keeps it only if it stays on this site, and checks that the path it hands back cannot be read as another host either. The path it returns is the parsed one, so `.` and `..` segments are resolved and characters such as spaces come back percent-encoded. A `callbackUrl` given twice in the same address used to make both pages fail with a server error; it now falls back to the dashboard like any other value that can't be used.
- SMTP on port 465 works without setting `SMTP_SECURE`. An unset or blank value was read as `false`, so the app spoke plain text to a port that expects TLS from the first byte, and every email failed, sign-in links included. Blank now picks from the port: TLS on 465, otherwise STARTTLS if the server offers it. `.env.example` used to ship `SMTP_SECURE=false`; if you copied that and use port 465, clear it. A mail host that is down or never greets now fails a send in about 10 seconds across the DNS lookup, every address tried, connection setup and greeting, rather than waiting up to 2 minutes per address; the sign-in request gives up on a send after 30 seconds rather than waiting on the mail server for up to 10 minutes.
- The commit sheet on `/s/[slug]` locks page scroll while it is open. It was a hand-rolled `fixed inset-0` overlay, so on a phone the list kept scrolling underneath it: the row you tapped slid away mid-form and the sheet read as a floating toast rather than a modal. It is now the shared `BottomSheet` the organizer UI already uses, which brings Escape-to-close, a focus trap, a real `role="dialog"`, hiding the rest of the page from assistive tech, a scrollable body under the 85vh cap (the form stays reachable with the keyboard up) and safe-area padding. The sheet's title carries the slot name, so the form body no longer repeats it as a heading; autofocus is now scoped to this dialog's own fields, where a document-wide query could focus another row's email input. Two consequences of moving to the shared component are worth knowing: the sheet/card breakpoint is `md` (768px) rather than the old dialog's `sm` (640px), so 640–767px viewports now get the full-width sheet instead of a centred card; and a commit in flight holds the sheet open against Escape, the backdrop and the close X alike, which is greyed out to match.
- The commit sheet is announced by the same disambiguated name as the button that opened it (`Sign up for Sat, May 16, Cookies, Vinland Elementary`), not the bare slot title. On a date-grouped signup every date has its own "Cookies", so the short name told a screen-reader user neither which slot they had landed on nor that the sheet was a sign-up form. On screen the heading stays the slot's own name and now wraps to two lines instead of truncating to one — it is the only place the sheet states the slot, and one clipped line lost the end of it at 390px.
- A commit error (a slot that filled up while you were typing, a rejected email) scrolls itself into view inside the sheet. It renders below the fields, so on a short viewport with the keyboard up the only visible sign of a failed submit was the buttons becoming live again.
- Slot rows on the public page no longer truncate their own details on a phone. A fixed right rail (a 36px count column and a 96px button column) left ~160px for text at 390px, so the single clamped meta line dropped its last segment — usually the location — from every row. The rail is now 80px below `sm` (96px above) and the meta line wraps instead of clamping. The text column measures 224px at 390px on an uncounted row and 176px on one that also shows a count; nothing clips at 360px or 390px. At 320px a counted row is still tight enough to clip its last meta segment.
- The `0/1` counter is gone from capacity-1 slots, which is most of them.
