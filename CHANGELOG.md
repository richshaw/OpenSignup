# Changelog

All notable changes to OpenSignup are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow semantic versioning.

## [Unreleased]

### Added
- Landing-page CTA click telemetry (`landing.cta_clicked` activity event).
- Initial v1 scaffolding: Next.js 15 + TypeScript + Drizzle + Auth.js v5 + pg-boss.
- Full entity schema (workspaces, organizers, members, signups, slot groups, slots, participants, commitments, activity, magic links, claims).
- Zod schemas as source of truth with discriminated union on `slot_type`.
- Capacity-safe commitment service with `(slot_id, position)` unique enforcement.
- Organizer magic-link login and personal-workspace auto-create.
- Mobile-first participant page with bottom-drawer commit flow.
- Reminder emails the day before a dated slot, via pg-boss.
- Pluggable email transport: console, SMTP, Resend.
- AGPL-3.0 license.
- Organizers can let participants sign up without an email (#378). The signup's `requireEmail` setting, on by default, can be turned off through the AI connector's `update_signup` tool or `PATCH /api/signups/[id]`; a switch on the Settings tab follows. With it off, the sign-up form's Email box says "(optional)" and starts blank, even for someone this browser remembers, and someone who leaves it blank gets no confirmation or reminder emails. Their link to change or cancel is not emailed: the confirmation screen shows it and says to save it, and the `os_commit` cookie keeps it in that browser. If the organizer turns it back on after the page loaded, the refused blank email turns the box required. In `POST /api/slots/[id]/commitments`, a blank, whitespace-only, null or missing `email` now means none: a signup that requires one refuses it with `invalid_input` on `email`, and one that doesn't always adds a new participant, as there is nothing to find them by. Turning the setting back on asks only new sign-ups: anyone already signed up without an email keeps their spot and can still change or move it. `get_signup` and the other connector tools now show `requireEmail`; `update_signup` advertises no default for any setting, so a client that fills in defaults cannot turn it back on with an unrelated change. The privacy and cookies pages and the help pages say what happens without an email.

### Changed
- Reminders are set on the date field itself: the field editor on the Build tab has a "Send a reminder email before this date" checkbox, one date field per signup carries it (a bell marks it in the fields list), and the Settings tab's reminders card is gone — Settings keeps only the danger zone.
- Reminders go out a fixed 24 hours before a slot. The per-signup lead time (`reminderLeadHours`, 2/24/48/72h) is gone: `slot_at` pins the organizer's wall clock to UTC because a signup carries no timezone, so a short lead was wrong by the organizer's UTC offset, and a longer one was rarely what anyone meant. Migration `0005` drops the stored value; `sendReminders` remains the only off switch.
- `settings.reminderFromFieldRef` is now always the date field slots take their instant from — calendar links, date ordering and reminder timing all read it. It is set on creation (the first date field), moved by the field services when that field is deleted or retyped, and refused by `PATCH /api/signups/[id]` when it names anything else; an omitted key keeps the current anchor instead of clearing it. Migration `0005` pins it on existing signups and rebuilds `slot_at` where the old auto-pick had resolved to nothing.
- The reminder time-of-day field is paired with the chosen date field rather than picked globally, so a return date can no longer be stamped with a departure time.
- The public signup page's header is the instance name alone, linked to the homepage. The landing page's example card, which mocks that page, drops the same segment and now reads its brand from `NEXT_PUBLIC_INSTANCE_NAME` instead of hardcoding "OpenSignup" (a self-hosted instance was showing someone else's brand in its own example). The `· Public signup` segment beside it named nothing a participant could act on — they arrive from a shared link, and the title and Sign-up buttons already say what the page is — and "Public" was ambiguous: true in the sense the product means it (no account, anyone with the link), but just as readable as "publicly listed", which these pages are not.
- Removed the orphaned `/app/signups/[id]/fields` and `/app/signups/[id]/slots` pages and the server actions only they used. Neither was reachable from the signup tabs; the Build tab already covers field and slot editing and grouping.
- Removed the unused idempotency-key store: `src/lib/idempotency.ts` was never called, so the `idempotency_keys` table was never written. Migration `0009` drops the empty table. The rate-limit table it shared a schema file with now lives in `src/db/schema/rate-limits.ts`.
- Removed four activity event types that nothing writes: `commitment.orphaned`, `signup.duplicated`, `reminder.scheduled` and `reminder.failed` (#244). `docs/telemetry.md` listed them as fired, and its reminder health query counted two of them, so those columns always came back 0; it now counts sends, and a separate query counts commitments with failed sends in pg-boss's own tables. The catalogue also gains the events it was missing (`slot.reordered`, `commitment.confirmation_sent`, `reminder.opted_out`, `reminder.opted_in`), its payloads and actors now match what the code writes, and it documents the organizer-actor `signup.viewed` the Build tab writes, which the example view counts now leave out. Comments that still described an `orphaned` commitment status, removed earlier, are corrected. `event_type` is plain text, so no migration is needed.
- A participant's `email` and `email_lower` may now both be null, for signups that make the email optional (#378). Migration `0011` drops the two `NOT NULL`s and adds a check that the columns are null together, and not blank when set; the unique index on `(signup_id, email_lower)` is unchanged, and lets any number of participants without an email share a signup. Such a participant gets no confirmation or reminder email, their edit page leaves the address out, the Responses tab shows "—" in its place ("No email" to a screen reader) and the CSV export an empty cell. `participantEmail` in the response to the token-authenticated `GET /api/commitments/[id]` can now be `null`.
- A move to another slot (`PATCH /api/commitments/[id]` with `swapToSlotId`) now returns the new commitment's `editToken` and `editUrl` alongside its fields, with the `edit`, `self` and `cancel` links signing up returns, and puts the new commitment in the returning-participant cookie in place of the old one. A participant without an email gets no confirmation of the move, so this is where they get the new edit link.

### Fixed
- A date field refuses a year before 1900 (#324). It took any four-digit year, and early ones broke things later: Postgres has no year 0, so a slot dated `0000-01-01` failed to save when that field set the slot's time, or broke a later field or settings change that moved the reminder date onto it; a year below 100 was stored correctly but read back a century late (`0099` as `1999`), including by the sign-up lockout check; and "Add to calendar" wrote a year below 1000 with too few digits. The error now says `"<ref>" must be a date in 1900 or later`; a day that doesn't exist, such as `2026-02-30`, still gets `"<ref>" must be a real date as YYYY-MM-DD`. The Build tab's date picker starts at 1900-01-01, the MCP tools' field guide names the floor, and Magic Compose leaves a drafted date that is early or doesn't exist blank, with a warning, where `createSignup` used to refuse the whole draft over it. A slot already holding such a date keeps it: saving that slot's values again asks for a date in 1900 or later, and a rebuild that reaches it gives it no reminder time instead of failing. Migration `0010` sets `slot_at` to null wherever it falls before 1900, so the lockout check and "Add to calendar" stop reading an early or misread instant straight away; the date itself stays in the slot's values. Every database connection the app opens now starts on UTC, whatever the database's default time zone: under a zone whose offset then had seconds in it, such as Amsterdam's before 1937, a slot dated in those years read back as an invalid date, which broke the public page and the lockout check. To see which slots still hold one (read-only): `SELECT s.slug, sl.id AS slot_id, f.ref, sl.values->>f.ref AS value FROM slots sl JOIN signups s ON s.id = sl.signup_id AND s.deleted_at IS NULL JOIN slot_fields f ON f.signup_id = sl.signup_id AND f.field_type = 'date' WHERE sl.values->>f.ref <> '' AND sl.values->>f.ref < '1900';`
- The SMTP login is no longer sent unencrypted when the mail server doesn't offer encryption (#330). On any port but 465, the default 587 included, the app switched to an encrypted connection only if the server offered STARTTLS in its first reply, so a server without STARTTLS, or anyone on the network who removed the offer, got `SMTP_USER` and `SMTP_PASSWORD` in plain text, then the email with its sign-in link and code. With a login set, the app now insists on STARTTLS and fails the send rather than going on without it. The error is "Error upgrading connection with STARTTLS" when the server refuses STARTTLS, or "EHLO failed but HELO does not support required STARTTLS" when it refuses EHLO, and either way it ends "The mail server did not accept STARTTLS. If it takes a login without encryption on a network you trust, set SMTP_REQUIRE_TLS=false." A server without a login is left as it was, deliberately, so a local test mail server with no TLS keeps working; set `SMTP_REQUIRE_TLS=true` to insist on encryption there too. **Before upgrading:** if your mail server takes a login but has no STARTTLS (a relay on your own private network, for example), set `SMTP_REQUIRE_TLS=false`, or every email will fail, sign-in links included.
- Changing "Group slots by" or "Send a reminder email before this date" on the Build tab no longer undoes setting changes made since the page opened (#314). The Build tab sent back its whole copy of the signup's settings from when the page loaded, with one value changed, and `PATCH /api/signups/[id]` replaced the stored settings with it. So a change made in another tab, or by an AI assistant through `update_signup` (turning reminders off, say), was quietly reverted the next time the Build tab saved either control. The Build tab now sends only the setting it changed, and `PATCH /api/signups/[id]` merges the settings it is given over the stored ones, as the AI assistant tools already did: a setting left out keeps its value, and `null` clears it (back to its default, where it has one), except `reminderFromFieldRef`, which keeps its date field whether it is left out or sent as `null`. A script that cleared a setting by leaving it out now has to send it as `null`. After a save the Build tab shows the settings the server returned, so reminders switched off elsewhere no longer still look on there. Two quick changes to these controls are saved one after the other, in the order they were made, so the server applies them in that order and the tab ends up showing the later one's result.
- A sign-in email that times out now has its real outcome logged (#332). The sign-in request stops waiting on a send after 30 seconds, but the send itself keeps going, and how it ended was thrown away, so the log said only "magic link send timed out after 30 s" even when the mail server went on to reject the login or the TLS connection. A send that ends after the limit now logs "magic link send failed after it timed out" with the mail server's error message and code, plus those of the error's cause (where a failed request to Resend keeps the real reason), or "magic link dispatched after its send timed out" when the email did go out, both with the recipient and how long the send took. Only the error's message and codes are logged, never the whole error or the email's contents, and any URL query string or six-digit number in that text is blanked in case the mail server quoted the email. The send is still not cancelled when the limit runs out; that is left for later.
- The sign-in page keeps the email address you typed when it shows an error (#50). It used to clear the box after any error — an address it couldn't read, a link that failed to send, or the sign-in rate limit — so fixing a one-letter typo meant typing the whole address again. Editing the address clears the error. After the rate limit, the button does nothing until the address is edited: every request counts against the IP address's allowance first, which everyone on a shared network shares, and clicking it again and again would use that up. After a link is sent the box still empties, ready for "Send again". The six-digit code box likewise keeps a wrong code, so one mistyped digit no longer means typing all six again.
- SMTP startup now rejects an incomplete credential pair instead of silently skipping authentication (#331). **Before upgrading:** if you set only `SMTP_USER`, add `SMTP_PASSWORD` or remove `SMTP_USER` for a server that needs no authentication; likewise, remove a lone `SMTP_PASSWORD` or add its user. An empty or whitespace-only `SMTP_USER` or `SMTP_PASSWORD` counts as unset. Spaces around `SMTP_USER` are trimmed; the password is used exactly as given, spaces included.
- A setting that holds only whitespace (spaces, a tab, a stray newline, or an invisible character pasted from a secrets dashboard) now counts as unset, the same as an empty one. So startup catches a blank `SMTP_HOST`, `RESEND_API_KEY`, `GOOGLE_CLIENT_ID` or `LLM_MODEL`, where before every email, Google sign-in or Magic Compose request failed later, and a required setting such as `AUTH_SECRET` reports that it is required. The error adds "Its value is only whitespace, which counts as unset." so a value you can't see is not a mystery. Settings with a development default (`EMAIL_TRANSPORT`, `NODE_ENV`, `NEXT_PUBLIC_APP_URL`, `AUTH_MAGIC_LINK_MAX_AGE_MINUTES`) still refuse a blank value rather than falling back to the default.
- The sign-in page no longer says a magic link was sent when sending it failed (#329). When the email can't go out (the mail server is down or too slow, or the request is over the sign-in rate limit), Auth.js logs the error and answers with its error page instead of throwing, and the page counted any answer that wasn't a throw as sent, so it showed "Sent — check your email" for a link that never left. It now counts a link as sent only when Auth.js answers with its check-your-email page, and otherwise shows "Couldn't send. Please try again." A request over the sign-in rate limit (5 links an hour for one address, 20 from one IP address) says so instead, since trying again at once would fail again: "Too many sign-in requests. Wait up to an hour. If we already emailed you a link, you can use that." It has no "Try again" link: every request counts against the IP address's allowance first, which everyone on a shared network shares. The limit counts in fixed hourly windows and applies to every address alike, known or not, so the message says nothing about whether an account exists. `sendVerificationRequest` throws the limit as `MagicLinkRateLimited` (`src/auth/magic-link-rate-limit.ts`), an `AuthError`, which Auth.js rethrows to the page's `signIn`; `POST /api/auth/signin/nodemailer` still answers with `/login?error=Configuration`, as before. The form's error text also shows in red now; it showed grey.
- A participant can no longer take more spots through their edit link once sign-ups have closed. Signing up, and moving to another slot, is refused when the signup is closed or archived, its closing time (`closesAt`) has passed, the slot is closed, or the slot is inside the signup's lockout window (`lockoutHoursBeforeSlot`), but raising the number of spots on a place already held checked none of these. So anyone already signed up could add spots after the organizer closed the signup or the slot. `PATCH /api/commitments/[id]` now refuses an increase with `closed` by the same rules, which signing up and the edit page now share, and logs it as a failed attempt like a refused sign-up. The edit page shows a "Sign-ups have closed" notice and no longer offers more spots than the participant holds, and a save refused because sign-ups closed after the page loaded says "Sign-ups have closed, so you can't add more spots." rather than the API's message. Lowering the number, changing a name or notes, and cancelling still work, since they only give places back or correct details.
- Deleting a signup now also stops its slots, fields, activity log and CSV export being served. The four organizer routes reading those never checked `deleted_at`, so a deleted signup kept answering on its id to members of its workspace — the export with every participant's name and email address — long after it had vanished from the organizer's list and the public page. The slots, activity and export routes now go through one `getSignupRowForOrganizer` in the signups service, and `listFields` behind the fields route checks `deleted_at` too. The activity route's `?limit=` is also rounded down to a whole number; a fraction such as `1.5` used to fail with a 500.
- A deleted signup no longer takes sign-ups or edits. Deleting keeps the signup's status as it was, and signing up checked only that status, so an open signup kept accepting people after it was deleted: anyone with the page still open, or a slot id, could sign up, and got a confirmation email for a signup the organizer thought was gone. Adding, editing or deleting a field, reordering slots and deleting a slot went through as well, each writing to the activity log of a signup that every read calls not found, and a participant's edit link still let them change their place or take more. The organizer's services and signing up now load a signup through `readLiveSignup` or the signup lock (`lockSignupForWrite`) in `src/services/locks.ts`, which both skip a deleted signup, the lock including one deleted while it waited. A participant's edit link is not found, like the signup's own page, including an edit or cancel that was waiting on a lock when the delete landed, and the confirmation email is not sent if the signup has been deleted by the time it goes out. Publishing, closing or archiving a signup that is deleted at the same moment is not found rather than a status change on the deleted row. On the sign-up sheet and the edit page, a slot or signup removed after the page loaded now reads "Sorry, this is no longer available" rather than the API's "not found". The privacy page said deleting a signup removes its commitments; it takes them off the site, but the rows stay in the database until someone asks for them to be erased, and it now says so.
- A post-login `callbackUrl` on `/login` or `/login/check` can no longer send the browser to another site. `safeCallbackUrl` checked the value as a string, but a browser drops tab, LF and CR characters before reading a URL, so a value that passed the check could still arrive as a link to another host. It now parses the value, keeps it only if it stays on this site, and checks that the path it hands back cannot be read as another host either. The path it returns is the parsed one, so `.` and `..` segments are resolved and characters such as spaces come back percent-encoded. A `callbackUrl` given twice in the same address used to make both pages fail with a server error; it now falls back to the dashboard like any other value that can't be used.
- SMTP on port 465 works without setting `SMTP_SECURE`. An unset or blank value was read as `false`, so the app spoke plain text to a port that expects TLS from the first byte, and every email failed, sign-in links included. Blank now picks from the port: TLS on 465, otherwise STARTTLS if the server offers it. `.env.example` used to ship `SMTP_SECURE=false`; if you copied that and use port 465, clear it. A mail host that is down now fails a send in about 10 seconds for each address its name resolves to (nodemailer tries them in turn) instead of 2 minutes for each, and the sign-in request gives up on a send after 30 seconds rather than waiting on the mail server for up to 10 minutes.
- The commit sheet on `/s/[slug]` locks page scroll while it is open. It was a hand-rolled `fixed inset-0` overlay, so on a phone the list kept scrolling underneath it: the row you tapped slid away mid-form and the sheet read as a floating toast rather than a modal. It is now the shared `BottomSheet` the organizer UI already uses, which brings Escape-to-close, a focus trap, a real `role="dialog"`, hiding the rest of the page from assistive tech, a scrollable body under the 85vh cap (the form stays reachable with the keyboard up) and safe-area padding. The sheet's title carries the slot name, so the form body no longer repeats it as a heading; autofocus is now scoped to this dialog's own fields, where a document-wide query could focus another row's email input. Two consequences of moving to the shared component are worth knowing: the sheet/card breakpoint is `md` (768px) rather than the old dialog's `sm` (640px), so 640–767px viewports now get the full-width sheet instead of a centred card; and a commit in flight holds the sheet open against Escape, the backdrop and the close X alike, which is greyed out to match.
- The commit sheet is announced by the same disambiguated name as the button that opened it (`Sign up for Sat, May 16, Cookies, Vinland Elementary`), not the bare slot title. On a date-grouped signup every date has its own "Cookies", so the short name told a screen-reader user neither which slot they had landed on nor that the sheet was a sign-up form. On screen the heading stays the slot's own name and now wraps to two lines instead of truncating to one — it is the only place the sheet states the slot, and one clipped line lost the end of it at 390px.
- A commit error (a slot that filled up while you were typing, a rejected email) scrolls itself into view inside the sheet. It renders below the fields, so on a short viewport with the keyboard up the only visible sign of a failed submit was the buttons becoming live again.
- Slot rows on the public page no longer truncate their own details on a phone. A fixed right rail (a 36px count column and a 96px button column) left ~160px for text at 390px, so the single clamped meta line dropped its last segment — usually the location — from every row. The rail is now 80px below `sm` (96px above) and the meta line wraps instead of clamping. The text column measures 224px at 390px on an uncounted row and 176px on one that also shows a count; nothing clips at 360px or 390px. At 320px a counted row is still tight enough to clip its last meta segment.
- The `0/1` counter is gone from capacity-1 slots, which is most of them. It made a reader decode a fraction to learn "nobody yet", which the Sign-up button already said, and it was unlabelled for screen readers ("zero slash one"). Real fractions (`2/4`, `10/12`) still show and now carry an sr-only sentence; a fixed-width column used to clip `10/12`. An uncapped slot no longer renders a bare, denominator-less `0`.
- Every state of a slot row's action occupies the same box. "Full" and "Closed" were narrow labels hugging the row's edge next to an 82px "Sign up" pill, so one control's states did not line up with each other down the column. They now share one box: 80px below `sm`, 96px above. Note this is a deliberate divergence from design-system/ui_kits/participant/SlotRow.jsx, which centres a content-width child in a 96px wrapper rather than making every state the same width — the kit correctly identifies the drift (`justify-end` where it should centre) but does not ask for this fix.
- The inert "Full"/"Closed" label is `text-sm`, matching the Sign-up button and Edit link it stands in for, and the size now lives in the shared `ACTION_SIZING` rather than at six call sites. This one goes against the design system, which documents `--text-xs` as "pill labels" and steps the inert label down a size from the action: the judgement here is that `text-ink-soft` already carries the de-emphasis and a second signal only made the column ragged.
- Each slot row's action is named after its own slot (`Sign up for Wed, Sep 30, vs Gerald`), not a bare `Sign up` repeated once per row, so a screen-reader user can tell which slot they are committing to. The name is built from the group label, the title and the meta segments together: on a signup grouped by date the title of every row is only its *time*, so title alone would have moved the collision rather than removed it.
- Row actions meet a 44px minimum touch target below `sm` (iOS HIG 44pt, Material 48dp). They measured 32px, in a list whose whole purpose is tapping one row out of many on a phone. From `sm` up they sit at 36px, the height the real Sign-up button already was, so the production button is unchanged on a pointer and the Edit link and Full/Closed label join it instead of sitting at 34px and 28px.
- Self-hosting with `docker-compose.prod.yml` works with the `.env` that `.env.example` produces (#236). Compose now builds `DATABASE_URL` from `POSTGRES_USER`/`POSTGRES_DB`, points it at the `db` service, and passes the password as `PGPASSWORD`, so it needs no URL-encoding; before, the copied `localhost` URL made the migrate step fail with `ECONNREFUSED`. Operators who run their own Postgres set `EXTERNAL_DATABASE_URL` instead: **if you already point this compose file at an external database through `DATABASE_URL` in `.env`, move that value to `EXTERNAL_DATABASE_URL` before upgrading**, or the app will use the empty bundled database.
- The Compose web container now passes its healthcheck. It pins `HOSTNAME=0.0.0.0` (Docker's default, the container id, left `127.0.0.1` unbound) and `PORT=3000` (a `PORT` in `.env`, meant for the host port, moved the server off 3000).
- Compose builds now pass `NEXT_PUBLIC_APP_URL` from `.env` to the build. Before, the build ignored it, so canonical links, `sitemap.xml`, `robots.txt` and Open Graph URLs always said `http://localhost:3000`. `.env.example` still ships that localhost value for local development, so self-hosters must set their own address; the build does not catch a value left unchanged.
- The README Quickstart works on a fresh clone. `.env.example` leaves the required branding values blank, so the first page load under `pnpm dev` threw `Invalid site config`; CI never saw it because it sets them. `pnpm dev` now fills blanks with obvious placeholders ("OpenSignup (dev)", `dev@example.com`, "your jurisdiction (dev placeholder)"). `pnpm build` and Docker builds still fail when they are missing.
- The Docker image no longer downloads pnpm each time the migrate or worker container starts: `COREPACK_HOME` gives the root build and the non-root `signup` user the same Corepack cache.
- Adding, editing or deleting a slot field now rebuilds `slots.slot_at`. Previously only deleting the chosen date field did, so a field change could leave some slots stale and others null depending on edit order.
- A signup with two date fields and no chosen one used to resolve to *no* date field, which silently switched off reminders and the "Add to calendar" button for the whole signup. Resolution no longer guesses; the anchor is always explicit.
- The build page now mirrors the server when a field change moves or drops the reminder anchor or the group-by field, so its next settings save cannot resurrect a field that no longer exists.
- Slot fields added without an explicit `sortOrder` now append instead of landing at position 0. The build page never sends one, so every field it added sorted ahead of the template's date column (`DEFAULT_TEMPLATE` pins it at 1) and reappeared mid-grid after a reload. Appends take a row lock on the signup so two concurrent adds cannot claim the same position.
- Landing-page JSON-LD no longer declares a `SoftwareApplication`, which Google's rich result requires to carry `aggregateRating` or `review`; it now describes the site and its publisher with `WebSite` + `Organization`.
- The landing page rendered two `<h1>` elements — the hero headline plus the example signup card. `SignupViewBody` now emits an `h2` in `showcase` mode.
- Meta descriptions on the landing page, root layout, and the three legal pages are within the 110–160 character range crawlers expect.
- The privacy, terms, and cookies pages now declare a self-referencing canonical URL.
- `/login` and `/login/check` now render the site footer, so both link to the privacy policy and terms.
- Slot `date` and `time` values are validated as real dates and times, not just as shapes: `2026-13-45`, `2026-02-30` and `99:99` are rejected on the way in, and `extractSlotAt` never stores an Invalid Date.
- A date-only slot is anchored at noon UTC rather than midnight, so its day-before reminder lands on the day before in every timezone from UTC-11 to UTC+11 (it used to arrive two days early for organizers west of Greenwich). Its calendar export is now an all-day event rather than a timed one at 12:00Z. Migration `0006` moves existing date-only slots.
- "Add to calendar" puts a timed slot at the hour the signup page shows (#304). The file wrote the slot's wall-clock time as UTC (`DTSTART:…Z`), so every calendar outside UTC moved it: a 3:15 PM slot in November showed at 7:15 AM in Los Angeles and 2:15 AM the next day in Sydney. A timed event's start and end are now floating times, with no `Z`, which calendar apps show at that hour in the viewer's own zone. `DTSTAMP` stays in UTC, and all-day events are unchanged. A participant whose device is set to another zone sees the same digits in that zone, as the signup page shows them.
- The AI connector's `update_signup` tool no longer takes `maxCommitmentsPerParticipant`, and its results no longer show it. Nothing checks that setting when someone signs up, so an assistant asked to limit each person to two spots reported the limit as set while anyone could still take every spot. A call that sends it is now refused with `invalid_input`, as is any other setting the tool doesn't list. The limit comes back once sign-ups enforce it.
